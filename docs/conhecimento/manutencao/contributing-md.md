# CONTRIBUTING.md

O arquivo **CONTRIBUTING.md** reúne as orientações para pessoas que desejam contribuir com um projeto. Ele descreve como a comunidade espera receber contribuições, quais processos devem ser seguidos e quais práticas ajudam a tornar a colaboração mais eficiente.

Normalmente localizado na raiz do repositório, esse arquivo funciona como um guia para novos e antigos contribuidores, reduzindo dúvidas e padronizando o processo de contribuição.

Embora seja amplamente utilizado em projetos Open Source, também pode ser adotado em projetos internos de empresas e organizações.

## Para que serve?

O principal objetivo do `CONTRIBUTING.md` é facilitar a colaboração.

Ele ajuda pessoas interessadas em contribuir a entender:

* como configurar o ambiente de desenvolvimento;
* como encontrar tarefas para contribuir;
* como reportar bugs;
* como sugerir novas funcionalidades;
* como abrir um Pull Request;
* quais padrões de código e documentação devem ser seguidos;
* como funciona o processo de revisão;
* quais são as expectativas da comunidade.

Ao centralizar essas informações, o projeto se torna mais acessível para novos colaboradores.

## Benefícios de utilizar um CONTRIBUTING.md

Um bom guia de contribuição oferece vantagens para toda a comunidade.

Entre os principais benefícios estão:

* reduz dúvidas recorrentes;
* facilita a entrada de novas pessoas no projeto;
* padroniza o processo de contribuição;
* melhora a qualidade das contribuições recebidas;
* reduz o tempo gasto pelos mantenedores respondendo perguntas repetidas;
* aumenta a consistência entre Pull Requests;
* melhora a experiência de quem contribui.

Para projetos Open Source, esse arquivo costuma ser um dos primeiros documentos consultados por quem deseja colaborar.

## O que normalmente contém?

Não existe um modelo único para um `CONTRIBUTING.md`, mas é comum incluir informações como:

* objetivo do projeto;
* formas de contribuir;
* configuração do ambiente de desenvolvimento;
* instalação das dependências;
* como executar testes;
* padrões de código;
* convenções de commits;
* fluxo de branches;
* como abrir Issues;
* como abrir Pull Requests;
* processo de revisão;
* canais de comunicação;
* referências para outros documentos do projeto.

Também é comum que o documento faça referência a arquivos como:

* `CODE_OF_CONDUCT.md`;
* `SECURITY.md`;
* `README.md`;
* documentação de arquitetura;
* guias de desenvolvimento.

## Exemplos de uso

Cada projeto adapta o `CONTRIBUTING.md` às suas necessidades.

Por exemplo:

* uma biblioteca pode explicar como executar a suíte de testes antes de abrir um Pull Request;
* um framework pode definir padrões para documentação e compatibilidade entre versões;
* um projeto de documentação pode explicar convenções de escrita e formatação;
* um projeto comunitário pode orientar como participar das discussões antes de propor grandes mudanças.

Independentemente do tipo de projeto, o objetivo é sempre reduzir barreiras para quem deseja colaborar.

## Todo projeto precisa de um CONTRIBUTING.md?

Não necessariamente.

Projetos pessoais, experimentais ou mantidos por uma única pessoa podem não precisar de um guia de contribuição, especialmente quando não esperam receber contribuições externas.

Por outro lado, o `CONTRIBUTING.md` passa a ser altamente recomendado quando o projeto:

* aceita contribuições da comunidade;
* possui múltiplos mantenedores;
* recebe Pull Requests regularmente;
* utiliza processos específicos para desenvolvimento;
* possui padrões de código ou documentação;
* exige etapas específicas para testes ou revisão.

Quanto maior o número de contribuidores e mais complexo o processo de desenvolvimento, maior tende a ser o benefício desse documento.

## Boas práticas

Ao escrever um `CONTRIBUTING.md`, recomenda-se:

* utilizar linguagem clara e objetiva;
* explicar cada etapa do processo de contribuição;
* assumir que a pessoa nunca contribuiu com o projeto antes;
* fornecer exemplos sempre que possível;
* incluir comandos de instalação e testes;
* manter links para outros documentos relevantes;
* revisar o conteúdo periodicamente para garantir que permaneça atualizado.

Um guia muito longo ou desatualizado pode acabar gerando mais dúvidas do que soluções.

## Documentação

Não existe uma especificação oficial para o `CONTRIBUTING.md`, mas diversas organizações e projetos Open Source publicam recomendações e modelos.

Uma das referências mais conhecidas é o guia **Open Source Guides**, da GitHub, que dedica uma seção às boas práticas para receber contribuições e estruturar projetos colaborativos.

Independentemente do formato adotado, o mais importante é que o documento seja claro, atualizado e compatível com o processo de desenvolvimento do projeto.
